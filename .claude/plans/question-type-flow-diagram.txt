BACKEND EVALUATION (Answer Judging)
───────────────────────────────────
Question Type + Metadata → get_eval_prompt() → Select evaluation rubric

Prompt selection logic:
  • SPEAK: Dynamic based on target_language ("for English speakers")
  • LISTEN_WRITE: Dynamic ("for English speakers")
  • EN_TO_CN: Explicit ("Expert Chinese Tutor for English speakers")
  • CN_TO_EN: Explicit ("Expert Language Coach")
  • PATTERN_DRILL: Explicit ("for Chinese Native Speakers")
  • JA_SPEAK, JA_LISTEN_WRITE: Explicit
  • {LANG}_VARIANTS: Derived from base type

⚠️ RISK: Audience is inferred from question_type, not explicit metadata


FRONTEND UI RENDERING (Practice Display)
────────────────────────────────────────
Question Type + Metadata → getQuestionTypeConfig() → Config object

Config resolution:
  • SPEAK → buildCanonicalSpeakConfig(metadata)
  • LISTEN_WRITE → buildCanonicalListenWriteConfig(metadata)
  • CN_TO_EN, EN_TO_CN → Hardcoded CONFIGS
  • CN_TO_{LANG} → Regex match, dynamic build
  • {LANG}_SPEAK → Pattern match, canonical builder
  • Unknown → FALLBACK_CONFIG

Config includes:
  • targetLanguage, supportLanguage (from metadata)
  • answerMode (text, speech, listen_write, pattern)
  • badgeLabel, promptLabel (localized)
  • theme (color scheme)


CANONICALIZATION CHALLENGE: Named → Generic Types

KEY COMPATIBILITY RISKS
───────────────────────

1. AUDIENCE INFERENCE IS IMPLICIT
   Current: question_type = "EN_TO_CN" → implies "for English speakers"
   Proposed: question_type = "TRANSLATE" + metadata
   Problem: Can't infer who should evaluate without explicit "evaluator_language"
   Impact: HIGH - Wrong evaluation prompt if inferred audience is wrong

2. NEW LANGUAGE PAIRS BREAK THEME LOGIC
   Current: Hardcoded theme per type (e.g., EN_TO_CN_SPEAK → rose)
   Proposed: Compute theme from target_language + answerMode
   Problem: No theme defined for all 100+ language pair combinations
   Impact: MEDIUM - New language pairs need theme assignment rules

3. MIGRATION OF ~5,000 EXISTING QUESTIONS
   Current: Old questions have question_type = "EN_TO_CN_SPEAK"
   Proposed: Change to "SPEAK" + fill metadata
   Problem: If metadata is wrong for even 1%, wrong prompts are used
   Impact: HIGH - Requires comprehensive validation before/after

4. FRONTEND PATTERN MATCHING BECOMES PERMANENT TECH DEBT
   Current: Frontend handles CN_TO_{LANG} patterns
   Proposed: All types should be canonical
   Problem: Old questions still have named types; pattern matchers must persist
   Impact: MEDIUM - Legacy code forever unless database is migrated

5. EVALUATION PROMPT AUDIENCE NOT TRACKED ANYWHERE
   Current: Audience is implicit in question_type
   Proposed: Audience should be explicit
   Problem: "PATTERN_DRILL for Chinese speakers" vs "PATTERN_DRILL for English speakers" not distinguishable
   Impact: MEDIUM - Can't change evaluation audience per question later


CRITICAL QUESTION
──────────────────
Should "evaluator_language" or "rubric_audience" be EXPLICIT metadata?

Without it:
  • Can't safely swap evaluation audience later
  • Prompt selection is brittle: "if target_language == en then English speaker"
  • Multi-evaluator scenarios (peer review) not supported

With it:
  • One extra field per question
  • Explicit, verifiable, changeable per question
  • Supports future audience variations

Recommendation: YES, add explicit evaluator_language metadata
before canonicalizing question types.
